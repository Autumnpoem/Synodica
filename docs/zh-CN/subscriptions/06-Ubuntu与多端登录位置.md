# Ubuntu 与多端登录位置

任务由哪个后端执行，就在哪个后端的运行用户下准备登录。电脑 App 或手机网页只是连接服务器时，在手机浏览器登录 Google、ChatGPT 或 Claude，不会自动让 Ubuntu 的官方工具登录。

统一后端已加入会话登录、多端同步、冲突提示和桌面远程连接。部署模板见 [Ubuntu 部署](../Ubuntu部署.md)，App 和浮窗操作见 [桌面端与新功能](../桌面端与新功能.md)。源码支持与公开服务上线是两步；此说明不表示已替你配置公网域名和 HTTPS。

## 两种运行方式

| 模式 | 模型请求由谁发起 | 官方工具登录放在哪里 |
|---|---|---|
| Mac 本地模式 | Mac 上的后端 | 启动该后端的 Mac 用户 |
| Ubuntu 中央后端 | Ubuntu 上的后端 | 运行该后端的 Ubuntu 用户 |

例如服务使用 `opengrokbot` 这个系统用户，就应为它准备官方工具登录。上面只是示例账号名，不代表服务器已经建立了这个用户。用 root 登录一遍，并不能让另一个普通用户自动获得凭据。

## Ubuntu 准备顺序

1. 确定后端使用的系统用户、HOME、工作目录和数据目录。
2. 在该用户环境安装所需官方工具，确认 `codex --version`、`claude --version`、`gemini --version` 能找到命令。
3. 按各家文档完成登录：Codex 可用设备码；Claude 和 Gemini 按官方交互授权流程操作。
4. Kimi Code 与 DeepSeek Key 通过这个办公室的服务商设置保存，输入前确认页面属于你自己的服务器。
5. 启动或按正常部署流程重启服务，再检查服务商和用量状态。

不要为了省事把 Mac 的全部配置、钥匙串或整个用户目录复制进镜像。需要迁移官方登录缓存时，逐家按官方支持的方式处理，先确认目标用户及权限，保留原有凭据。

## systemd 和容器要核对什么

systemd 不一定继承你终端中的 PATH。服务进程必须能找到官方工具，HOME 也应指向预期的服务用户目录。不要把真实 Key 直接写进公开的服务示例或版本库。

容器运行时，要分别持久化办公室数据和官方工具所需的登录配置。仅持久化聊天数据，不代表工具登录也会保存。原有登录文件、配置目录和凭据存储的实际位置，以官方工具版本和部署方式为准；不要盲目挂载整个 HOME。

## 电脑和手机共享什么

连接同一个办公室后，应共享对话、项目、任务、审批、纠正记录和服务器账户的用量状态。这里的用量属于执行后端的账号，不是每台设备各自的一套额度。

桌宠在 Windows 或 Mac App 的透明窗口里运行，跟随所选办公室的状态。无图形桌面的 Ubuntu 运行宠物宿主，客户端负责显示。服务器与 App 需使用包含远程桌宠页面的同版本前端。

## 排查本地成功而服务器失败

依次核对：后端用户是否一致 → HOME 是否正确 → CLI 是否在服务的 PATH 中 → 登录是否属于目标订阅账号 → 成员选择的服务商和模型是否正确。不要先导出全部凭据或重新登录所有账号。
